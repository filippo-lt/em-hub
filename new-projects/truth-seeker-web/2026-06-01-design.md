# Truth Seeker Web — V1 Design

**Date:** 2026-06-01
**Status:** Draft for review
**Briefing:** `APPS-Briefing - Web Version for Truth Seeker-010626-144945.pdf`

---

## Executive summary

Truth Seeker Web is the browser counterpart to the Truth Seeker / People Finder mobile app. V1 is an MVP focused on the **People** lookup, sufficient to open paid acquisition channels and validate ROAS against portfolio benchmarks (D4 10–15%, D7 15–18%, D30 40–50%, trial conversion ≥10%).

The system is built as a **single Next.js application on Cloud Run**, with the search orchestration ported from the existing Python `deepsearch-service` to TypeScript (running in-process), Firebase Auth + Firestore for identity and app data, the **Parapet** quota service for token-based credits, and **Stripe** for subscription billing. The paywall is in-house using Stripe Payment Element with Firebase Remote Config–driven variants, designed as a swap seam for a future Superwall Web spike.

The existing mobile `deepsearch-service` (Python) is left untouched; the web codebase is standalone. The `qr-now-web-` scaffold is reused for stack and CI/CD patterns, but the QR domain code and Supabase layer are dropped.

---

## Locked architectural decisions

| # | Decision | Rationale |
|---|---|---|
| Q1 | **Fork/rewrite** `deepsearch-service` into the web app — do not extend the mobile service | Mobile service is device-id + RevenueCat-shaped; web is user-id + Stripe-shaped. Web↔mobile entitlement unification is explicit V1 out-of-scope per briefing. |
| Q2 | **Stripe → Parapet directly** — no RevenueCat in the web loop | Parapet's current version natively supports both Stripe and RevenueCat. RevenueCat in the web path adds a hop with no V1 benefit. |
| Q3 | **Firebase Auth + Firestore** for identity and app data | Briefing already mandates Firebase Web SDK (Remote Config) + GA4 + BigQuery export — adding Auth has near-zero marginal cost and pre-pays the V2 web↔mobile identity unification. |
| Q4 | **Full rewrite of search orchestration to TypeScript** in Next.js API routes (Vercel AI SDK + Zod + Tavily REST + OpenRouter via OpenAI-compatible client), gated by an eval set | Python orchestration is ~600 LOC of straight-line code using `create_agent`'s default ReAct loop with structured output — no custom LangGraph topology. TS equivalent is shorter. Eval gate converts "silent quality regression" into a one-day check. |
| Q5 | **Token-based quota model** — single token wallet, two costs (list = 1 token, detail = 3 tokens, values in Remote Config) | Matches briefing's ClarityCheck reference ("aggressive credit-pack upsells"); maps directly to the Python service's existing `people_search_cost` / `people_detail_search_cost` configuration; one wallet handles both subscription refresh and V2 credit packs. |
| Q6 | **Stripe Payment Element + Firebase Remote Config–driven paywall variants**, with the paywall built as a swap seam (single `<Paywall>` component contract `{variant, onSuccess}`). Superwall Web spike deferred to post-V1. | Briefing's PO already investigated Superwall Web and flagged it as "limited"; V1 ships in-house. Component-isolated paywall means future Superwall swap is a component replacement, not a refactor. |
| Q7 | **English only at V1 launch**, codebase fully i18n-ready (next-intl wired, locales array `['en']`) | One market gives a clean ROAS read; EU adds GDPR + cookie banner + data-rights flows as a hard legal-calendar blocker. ES + EU locales planned for V2. |

**Shape:**

- **One Next.js deployable** — public SEO pages, authenticated app, and BFF/search API routes all in the same Next.js app.
- **Cloud Run, not Vercel** — keeps the deployment in the existing GCP project (Firestore, Cloud Build, IAM), and avoids Vercel's function-timeout cliff for long-running search calls. Reuses `qr-now-web-`'s `cloudbuild.yaml` + `terraform/`.
- **External services:** Tavily (search), OpenRouter (LLM router, OpenAI-compatible API), Stripe (billing), Parapet (token wallet).
- **Firebase products used:** Auth, Firestore, Remote Config, GA4. Admin SDK on the server, JS SDK on the client.

**Reuse from `qr-now-web-` scaffold:**

- Next.js 16 App Router + Tailwind + shadcn/ui
- Stripe webhook scaffolding (rewired for Payment Element + subscription flow)
- next-intl i18n wiring (locales reduced to `['en']`)
- Dashboard/settings layout patterns
- `cloudbuild.yaml` + `terraform/`
- Husky/eslint/CI config

**Dropped from scaffold:**

- Supabase Auth + Postgres + RLS schemas
- Stripe Checkout flow (replaced by Payment Element)
- QR domain code

## Section 3 — Data model

Three stores, each with clear ownership:

| Store | Owns | Reasoning |
|---|---|---|
| **Firebase Auth** | User identity (uid, email, providers) | Source of truth for "who is this user" |
| **Firestore** | User profile, search history, search results | App data, needs queries/joins/secure rules |
| **Parapet** | Token balance, entitlement state | Quota service per Q2 |

Stripe sits outside but is linked via `stripeCustomerId` and `Customer.metadata.firebase_uid`.

### Firestore collections

```
users/{uid}                              ← keyed by Firebase uid
  email: string
  displayName: string?
  photoURL: string?
  createdAt: timestamp
  lastSeenAt: timestamp
  stripeCustomerId: string?              ← set at first checkout
  planStatus: 'free'|'trial'|'pro'|'canceled'|'past_due'  ← UI cache, source = Stripe
  planRenewsAt: timestamp?
  lastEntitlementSync: timestamp?        ← self-healing for missed Parapet webhooks
  locale: 'en'
  preferences: { darkMode: boolean, emailNotifications: boolean }

users/{uid}/searches/{searchId}          ← history list (lightweight)
  type: 'people-list' | 'person-detail'
  query: string
  searchCategory: SearchCategory
  preview: { ... }                       ← small snapshot for history UI
  resultRef: string                      ← path → searchResults/{id}
  tokensUsed: number
  durationMs: number
  status: 'completed'|'failed'
  createdAt: timestamp

searchResults/{searchId}                 ← full report bodies (separate collection)
  userId: string
  type: 'people-list'|'person-detail'
  request: { query, category, context? }
  response: { ... }                      ← full structured response
  llmModel: string
  agentSteps: number
  createdAt: timestamp
  ttl: timestamp                         ← Firestore TTL auto-delete (90d, configurable)

stripeEvents/{eventId}                   ← webhook dedup
  receivedAt: timestamp
  type: string
```

**Why two collections for searches:** `searches/` is small + indexed for the history list (`orderBy createdAt desc`); `searchResults/` holds the heavy report bodies separately so the history list reads stay cheap and we can TTL the heavy data without losing the history index.

**What is deliberately NOT in Firestore:**

- Token balance — Parapet is source of truth; we read on demand from API routes.
- Subscription state — Stripe is source of truth; `planStatus` on `users/` is a UI cache only.
- Events / analytics — Amplitude is the SoT; no `events/` collection.
- Notifications queue — "email when report ready" is fire-and-forget at end of search.

### Parapet linkage

- `parapet.userId` = Firebase `uid` (one-to-one for V1; aliases reserved for V2 mobile↔web unification).
- `parapet.identifier` = `com.truthseeker.web` (or equivalent bundle id configured in Parapet CRM).
- **One token wallet, two costs:**
  - `tokenKey: searchTokens` — single balance.
  - `incrementQuota: 1` for people-list, `incrementQuota: 3` for person-detail (values from Remote Config).
- **Stripe → token mapping** configured in Parapet CRM:
  - Trial purchase → initial grant (e.g., 3 tokens).
  - Pro subscription → monthly refresh of N tokens.
  - Credit packs (V2) → one-time additive grant.

### Stripe linkage

- `stripeCustomerId` written to `users/{uid}` at first checkout.
- Stripe `Customer.metadata.firebase_uid` set at customer creation — used by Parapet's Stripe webhook to map back to `parapet.userId`.
- **Two independent webhook subscribers** on the same Stripe events:
  1. Our `/api/billing/webhooks/stripe` → updates `users/{uid}.planStatus`, sends emails.
  2. Parapet's own Stripe webhook → tops up token wallet.
- Both idempotent on Stripe `event.id`.

### Firestore security rules (sketch)

```
match /users/{uid} {
  allow read: if request.auth.uid == uid;
  allow write: if request.auth.uid == uid
               && !affectsServerOnlyFields(request.resource.data);
  // Server-only fields: stripeCustomerId, planStatus, planRenewsAt, lastEntitlementSync
}
match /users/{uid}/searches/{searchId} {
  allow read: if request.auth.uid == uid;
  allow write: if false;                 // only Admin SDK
}
match /searchResults/{searchId} {
  allow read, write: if false;           // only Admin SDK, via API routes
}
match /stripeEvents/{id} {
  allow read, write: if false;
}
```

### Retention + danger zone

- `searchResults/` Firestore TTL = 90 days (Remote-Config-driven).
- "Reset searches" deletes all `users/{uid}/searches/*` + their `searchResults/*` via a server route.
- "Delete account" deletes all of the above + Firebase Auth user + cancels Stripe subscription + revokes Parapet identity.

### Eval fixtures

Lives in-repo at `lib/search/eval/fixtures.json` (15–20 queries spanning all 9 SearchCategory values + a baseline set). Not in Firestore — it is test data, not user data, and must be version controlled.

## Section 4 — Data flows (key user journeys)

### Flow 1 — Anonymous → first search → paywall → trial → full report

```
Browser            Next.js (RSC/API)       Firebase     Tavily/LLM    Stripe       Parapet
  │                       │                    │            │            │            │
  │ GET /[locale]         │                    │            │            │            │
  ├──────────────────────►│ SSG render         │            │            │            │
  │◄──────────────────────┤ landing + widget   │            │            │            │
  │                       │                    │            │            │            │
  │ submit search         │                    │            │            │            │
  ├──────────────────────►│ no auth → 401      │            │            │            │
  │◄──────────────────────┤                    │            │            │            │
  │                       │                    │            │            │            │
  │ /signup (Google SSO)  │                    │            │            │            │
  ├──────────────────────►│ ────► createUser ──►│            │            │            │

  │                       │ ◄──── trimmed structured response ◄──────────             │
  │                       │ write searchResults/{id}        │            │            │
  │                       │ write users/{uid}/searches/{id} │            │            │
  │                       │ DON'T decrement (no tokens)     │            │            │
  │◄──────────────────────┤ return PREVIEW only (paywallRequired=true)               │
  │                       │                    │            │            │            │
  │ click "Start Trial"   │                    │            │            │            │
  ├──────────────────────►│ /api/billing/checkout-session   │            │            │
  │                       │ stripe.customers.create({metadata.firebase_uid}) ────────►│
  │                       │ ◄──── customer_id ◄──────────────────────────             │
  │                       │ write stripeCustomerId          │            │            │
  │                       │ stripe.subscriptions.create(trial, payment_behavior=default_incomplete) ─►│
  │                       │ ◄──── client_secret ◄────────────────────────             │
  │◄──────────────────────┤ { clientSecret, variant }       │            │            │
  │                       │                    │            │            │            │
  │ Payment Element confirms on-page ──────────────────────────────────► Stripe       │
  │                       │ ◄──── invoice.paid + subscription.created (webhook) ─────│
  │                       │ (fan-out: Flow 3)               │            │            │
  │                       │                    │            │            │            │
  │ redirect /app/search/{id}                  │            │            │            │
  ├──────────────────────►│ parapet.checkTokens ───────────────────────────────────► │
  │                       │ ◄──── { balance:3, canUse:true } ◄──────────────────────  │
  │                       │ read searchResults/{id}         │            │            │
  │                       │ parapet.decrementTokens(uid, searchTokens, 1, jwt) ───── │
  │◄──────────────────────┤ FULL report                     │            │            │
```

**Key points:**

- Search runs *before* paywall, so we can show a preview without burning the LLM call for nothing. The first anonymous-to-trial search is a bounded sunk cost.
- Decrement happens only after payment lands and the user views the full report.
- Auth gate is at search submit, not landing — landing is SSG and indexable.
- `stripeCustomerId` is added at first checkout, not at signup (users who never pay don't create Stripe customers).
- Trial uses Stripe's `default_incomplete` subscription pattern → Payment Element confirms client-side → webhook completes server-side.

### Flow 2 — Returning paid user runs a search (steady state)

```
Browser                Next.js API                Firebase       Tavily/LLM    Parapet
  │                         │                         │              │            │
  │ POST /api/search/people-list                      │              │            │
  ├────────────────────────►│ verifyIdToken ─────────►│              │            │
  │                         │ parapet.checkTokens(uid, searchTokens) ────────────►│
  │                         │ ◄──── { balance:42, canUse:true } ◄──────────────  │
  │                         │ orchestrator.peopleList()              │            │
  │                         │ ──── agent loop (Tavily ↔ LLM) ───────►│            │
  │                         │ ◄──── structured response ◄────────────             │
  │                         │ write searchResults/{id}               │            │
  │                         │ write users/{uid}/searches/{id}        │            │
  │                         │ parapet.decrementTokens(uid, searchTokens, 1, jwt) ►│
  │                         │ ◄──── { newJwt } ◄──────────────────────────────── │
  │                         │ trigger email (fire-and-forget) ─► Resend          │
  │◄────────────────────────┤ { report, balance:41, newJwt }                     │
```

**Key points:**

- Tokens checked *before* the LLM call to short-circuit on zero-balance (cheap fail).
- Tokens decremented *after* successful search — failed searches don't burn tokens.
- The new Parapet JWT flows back to the client and is stored alongside the Firebase ID token.

### Flow 3 — Stripe webhook fan-out (subscription created / renewed / canceled)

```
Stripe                Next.js webhook        Parapet webhook     Firestore     Resend
  │                         │                       │                 │            │
  │ customer.subscription.created ─────────────────►│                 │            │
  │                         │                       │ map customer.metadata.firebase_uid → parapet.userId
  │                         │                       │ apply token grant per product config
  │                         │                       │                 │            │
  │ customer.subscription.created (parallel delivery)                │            │
  ├────────────────────────►│ verify signature      │                 │            │
  │                         │ dedupe by event.id (Firestore stripeEvents/) ──────►│
  │                         │ lookup user by stripeCustomerId        │            │
  │                         │ write users/{uid}.planStatus           │            │
  │                         │ send welcome email ─────────────────────────────────►│
  │                         │ 200 OK                                  │            │
  │◄────────────────────────┤                                         │            │
```

**Key points:**

- Two independent webhook subscribers on the same Stripe events. Each is idempotent on its own side; failure of one does not affect the other.
- Webhook dedup via Firestore: `stripeEvents/{event.id}` written transactionally with the handler's primary write. Second delivery short-circuits.
- Subscription-canceled flow: Parapet stops top-ups at end of period; our webhook flips `planStatus` to `'canceled'`. Token balance keeps draining naturally — the user uses remaining tokens until empty.

## Section 5 — Error handling

### Search failures — never burn a token on failure

| Failure | Cause | Handling | Token burned? |
|---|---|---|---|
| Tavily empty / 5xx | Provider down, no matches | Return empty structured response | No |
| LLM provider 5xx / 429 | OpenRouter rate-limit or upstream model down | Vercel AI SDK exponential backoff (3 attempts); fallback model from Remote Config; throw `SearchRetryableError` if both fail | No |
| Agent hits `maxSteps: 10` | Equivalent of Python `GraphRecursionError` | Return empty response, Sentry P2 (quality signal) | No |
| Zod validation fails | LLM produced malformed JSON | Retry once with stricter prompt suffix; if still bad, return empty + Sentry P2 | No |

**Contract:** API routes only decrement tokens *after* a successful structured response has been written to Firestore.

### The dangerous edge: search succeeded, decrement fails

**V1:** search first, decrement after, accept the leak; Sentry P1 alert on every occurrence; daily reconciliation script (`pnpm scripts:reconcile-decrements`) cross-checks `searchResults/` from last 24h against Parapet history.

If P1 fires more than ~1×/week post-launch, upgrade to a pending-decrement queue (`pendingDecrements/{id}` Firestore docs with a scheduled reconciliation worker). Do not pre-build the queue.

### Stripe webhook robustness

- Invalid signature → 401, Sentry P1, no processing.
- Duplicate delivery → dedupe via `stripeEvents/{event.id}` Firestore doc; second delivery short-circuits.
- Handler crash mid-processing → 5xx returned so Stripe retries (3-day retry window).
- Customer not found in Firestore → 200 + Sentry P2 (stops Stripe retries).
- **Self-healing for missed Parapet webhooks:** if `users/{uid}.lastEntitlementSync` is >5 min stale AND `planStatus === 'pro'`, the API route force-refreshes Parapet by calling its sync endpoint before proceeding.

### Auth boundary

- Expired Firebase ID token → 401 with `code: 'auth/id-token-expired'`; client refreshes via `getIdToken(true)` and retries once.
- Stale Parapet JWT → API route fetches a fresh JWT via Parapet S2S; client never sees this.
- Missing/tampered session cookie → 401, redirect to `/login` with `returnTo` param.

### Firestore write ordering for a successful search

1. Write `searchResults/{id}` (heavy doc) — failure → return error, no decrement, no history pointer left dangling.
2. Write `users/{uid}/searches/{id}` (history pointer) — failure → P2 (the result exists but won't appear in history; backfillable).
3. Decrement Parapet — fail path covered above.

### User-facing error UX

| Situation | UI | Recovery |
|---|---|---|
| Search failed (retryable) | Inline "Couldn't complete search — try again" + retry button | One click, no token cost |
| Search returned empty | "No results found" + suggestion to broaden | New search |
| Token wallet empty | Paywall variant: "You've used your last token" | Buy credit pack (V2) or upgrade |
| Subscription past-due | Banner + link to Stripe portal | 3-day Stripe grace period |
| Auth expired | Silent token refresh, retry once; on 2nd failure → `/login` | Sign back in |
| Payment Element error | Inline Stripe-provided error message | Retry on same screen (no subscription created, `default_incomplete` guarantees this) |

### Observability

- **Sentry**: all server-side throws + client errors. P1 = revenue/auth/payment; P2 = quality.
- **Amplitude events**: `landing_page_view`, `search_submitted`, `search_failed`, `paywall_viewed`, `trial_started`, `trial_converted`, `subscription_active`, `cancellation`. Naming aligned to mobile app's schema per briefing.
- **GA4 + BigQuery export** per briefing.
- **Cloud Logging** with `userId` + `searchId` + `requestId` correlation IDs.

## Section 6 — Testing strategy

### Layer 1 — The eval gate (launch criterion)

**Shape:**

- `lib/search/eval/fixtures.json`: 18 queries covering all 9 SearchCategory values + 9 "everything" baseline queries (well-known public figures, ambiguous names, edge cases like single-word names, non-Latin names).
- For each fixture, run once against the **Python `deepsearch-service`** (existing prod) and capture into `baselines/python/{fixtureId}.json` — one-time pre-port baseline.
- After the TS port, run the same fixtures against the TS orchestrator → `outputs/ts/{fixtureId}.json`.

**Comparison — structural, not exact-match** (LLM outputs are non-deterministic). Per fixture, assert:

- Zod schema validation passes with no errors.
- `people-list`: `len(people) >= floor(baseline_count * 0.7)` AND name-set Jaccard ≥ 0.5 AND at least one top-3 result overlaps.
- `person-detail`: `len(sources) >= floor(baseline_sources * 0.7)` AND answer length within ±30% of baseline AND name matches.
- No agent-recursion errors, no schema-retry failures, no thrown exceptions.

**Pass threshold:** 14/18 fixtures (78%) to greenlight V1 launch. Zero hard failures required.

**Run command:** `pnpm eval` — runs against the TS orchestrator, prints a table, exits non-zero on threshold failure. Wired into CI as a gating job. Also scheduled weekly post-launch (Cloud Scheduler) to catch provider/prompt drift.

### Layer 2 — Unit tests (pure logic only)

Test where logic is non-trivial and pure. Skip thin glue.

| File | Tested |
|---|---|
| `lib/search/tools/tavily.ts` | `trimTavilyResults()` — input shape variants, truncation, empty input |
| `lib/search/schemas.ts` | Zod schema parsing — happy, missing/extra fields, bad enums |
| `lib/stripe/webhook-handlers.ts` | Event → action mapping (table-driven), idempotency key derivation |
| `lib/parapet/tokens.ts` | Cost-lookup logic, JWT extraction |
| `lib/search/orchestrator.ts` | Agent loop terminates with mocked LLM + Tavily; decrement never called on failure |

**Not unit-tested:** API route handlers (thin), React components, Firebase Admin / Stripe SDK calls.

Target: ~30 tests, <5s, run on save.

### Layer 3 — Integration tests (Vitest + emulators + MSW)

Firebase Emulator Suite for Firestore + Auth. Stripe, Parapet, Tavily, OpenRouter mocked at the HTTP boundary (MSW).

**Critical scenarios:**

- Search happy path → Firestore write ordering correct, decrement after writes, return shape correct.
- Search fails at Tavily → no decrement, no history write, retryable error.
- Search succeeds but decrement fails → Sentry called, search result returned, P1 logged.
- Token-zero short-circuit → Tavily/LLM never called, paywall flag returned.
- Stripe webhook duplicate delivery → second call 200, no second write.
- Stripe webhook missing customer → 200 + Sentry P2.
- Stale ID token → 401 with correct error code.
- Account deletion → cascade through Firestore + Stripe cancel + Parapet revoke.

Target: ~15 tests, <30s, run on every PR.

### Layer 4 — E2E tests (Playwright, against staging)

Real services in test mode (Stripe test, Parapet staging, Firebase dev project, OpenRouter real with small budget).

1. **Conversion funnel:** anonymous → signup → search → preview → paywall → Payment Element with `4242 4242 4242 4242` → trial active → full report → token balance shown.
2. **Returning user steady state:** sign in → search → history → click history → see report → run another search.
3. **Account lifecycle:** signup → upgrade → cancel → access during grace period → delete account → verify auth + Firestore + Stripe + Parapet cleanup.

Run after every deploy to dev. Failures block prod promotion. Target: 3 specs, ~5 min total.

### Layer 5 — Manual launch checklist

- Apple Pay button renders on Safari iOS.
- Google Pay button renders on Chrome.
- 3DS flows on EU test cards.
- Welcome / trial-converted / payment-failed emails hit inboxes (not spam).
- Sitemap renders, robots.txt blocks `/app/*`, landing indexable via Google Search Console fetch-as.
- Remote Config knobs round-trip (console change reflected within cache TTL).
- Sentry receives errors from both client and server.
- Amplitude event names match mobile schema (one-pass verification).
- GA4 events in DebugView.

```
PR opened/updated:
  ├─ lint

Main merge:
  ├─ all PR checks
```

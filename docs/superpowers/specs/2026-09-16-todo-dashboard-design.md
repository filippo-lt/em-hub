# Todo dashboard design

Date: 2026-09-16
Status: approved, ready for implementation plan

## Problem

Action items from 1:1s live in `people/*/transcripts/*_analysis.md` as markdown
tables. Once the analysis is written, nothing surfaces them again until the next
`/prep` run pulls carry-overs. Items that belong to no upcoming 1:1 go quiet
entirely. The Sept 15 David analysis shows the cost: row 7 of its action table is
"August metrics sheet in Forward, You, today (you committed), 5th meeting".
Five meetings of slippage on an item that was written down every time.

There is no single place that answers "what do I owe, and to whom, right now".

## Goal

One live page showing every open loop, with three ways for items to get onto it:
by hand, from a 1:1 analysis, and from a scheduled sweep of Granola meetings that
have not been processed yet. Machine-proposed items wait for a click before they
join the list.

Reference: the existing artifact `GWpgojE8wLJx6tGwYqJ21m` ("Filippo's Open Loops").
This design keeps its inbox-gate idea and its `db` storage, changes the default
grouping, adds owner tracking, and drops its contradiction-flag panel.

## Non-goals

- Replacing the analysis documents. The dashboard points at them, it does not
  store the reasoning.
- Two-way sync with Jira. Jira tickets are the team's work. This list is Filippo's.
- A contradiction or inconsistency feed. The reference artifact had one. The
  analysis docs already do that job better.
- Multi-user access. One person uses this page.

## Storage

The artifact `db` capability holds everything. Three collections.

### `items/`

The accepted list. One document per open loop.

| Field | Type | Notes |
| --- | --- | --- |
| `text` | string | What needs to happen. One sentence. |
| `project` | string | Free text, drawn from `meta/sync.projects` |
| `owner` | string | `"me"`, or a person's display name |
| `priority` | string | `P0`, `P1`, `P2` |
| `due` | string or null | ISO date `YYYY-MM-DD` |
| `source` | object | `{kind, person, date, meetingTitle, granolaId}` |
| `done` | boolean | |
| `doneAt` | string or null | ISO timestamp |
| `verify` | boolean | True when the item may already be finished |
| `createdAt` | string | ISO date |
| `order` | number | `Date.now()` at creation, for stable sort |

`source.kind` is one of `manual`, `1on1`, `meeting`.

### `inbox/`

Proposed items awaiting triage. Same fields as `items/`, minus `done`, `doneAt`
and `order`, plus:

| Field | Type | Notes |
| --- | --- | --- |
| `why` | string | The transcript quote that produced the item |
| `proposedAt` | string | ISO timestamp |

Accepting a document moves it to `items/` and deletes it from `inbox/`. Skipping
deletes it. On accept the page fills the fields `inbox/` does not carry:
`done: false`, `doneAt: null`, `order: Date.now()`. It drops `why` and
`proposedAt`. Both operations are single writes from the page.

### `meta/sync`

One document.

| Field | Type | Notes |
| --- | --- | --- |
| `lastRun` | string | ISO timestamp of the last sweep |
| `lastGranolaTs` | string | Watermark. Meetings at or before this are done. |
| `processedIds` | array | Granola meeting ids already extracted. Capped at 200, oldest dropped. |
| `projects` | array | Known project names, for the add form and chips |
| `people` | array | Known owner names |

`processedIds` exists because Granola timestamps are not reliable enough on their
own. A meeting edited after the fact can move. The id list is the real guard, the
timestamp is the cheap prefilter.

## Derived state

Horizon is computed in the page from `due` and today's date. It is never stored,
so an item cannot sit in a stale bucket.

```
overdue     due < today
today       due == today
this week   due <= end of the current ISO week
this month  due <= end of the current month
someday     due is null, or beyond this month
```

One exception. A P0 with no due date sorts into "today", not "someday". A P0 that
nobody dated is still urgent by definition, and burying it defeats the point.

## Write paths

| Path | Trigger | Writes to | Gate |
| --- | --- | --- | --- |
| Manual | The add form on the page | `items/` | None |
| Post 1:1 | `/1on1-lifecycle` step 4.5 | `inbox/` | Accept per item |
| Sweep | Cloud routine, 08:00 Mon to Fri | `inbox/` | Accept per item |

Nothing generated by a model lands in `items/` without a click.

### Post 1:1 write

`/1on1-lifecycle` gains a step between memory extraction and keeping source docs
current. After writing the analysis file, it reads its own `## Action items`
table, converts each row to an `inbox/` document, and reports how many it queued.
Rows owned by the user become `owner: "me"`. Rows owned by anyone else become
`owner: "<that name>"`.

The step writes through `ArtifactData`. If the tool is unavailable the step logs
a line and continues. A failed todo push must never break a 1:1 write-up.

### Sweep

A `/schedule` cloud routine. Weekdays at 08:00.

1. Read `meta/sync`.
2. List Granola meetings newer than `lastGranolaTs`.
3. Drop any whose id is in `processedIds`.
4. For each remaining meeting, fetch the transcript and extract commitments,
   both Filippo's own and those other people made to him. Each extracted item
   carries the quote that produced it.
5. Deduplicate against open `items/` and pending `inbox/` on `granolaId` plus
   normalised text. Normalisation lowercases, strips punctuation, and collapses
   whitespace.
6. Write survivors to `inbox/`.
7. Update `lastRun`, `lastGranolaTs` and `processedIds`.

Extraction is a model pass, not a regex. The `## Action items` tables drift in
shape between analyses. The Sept 15 David file has a leading `| # |` column that
the `analyse` skill template does not define. Any parser tight enough to be
correct on one file breaks on the next.

The prompt lives in `.agents/agents/todo-sweep-agent.md` so the routine and a
manual run share one definition.

### Open assumption

The routine needs both the Granola connector and `ArtifactData` in its
environment. I have not verified that a cloud routine gets both. Implementation
checks this before the routine is written. If either is missing, the fallback is
a local launchd job in em-hub, and the change gets reported rather than made
quietly.

## Page

Single HTML file, `todos/dashboard.html`, published as an artifact with the `db`
capability. The file stays in git as the source, the artifact is the running copy.

Layout top to bottom:

1. Stat strip. Overdue count, this-week count, waiting-on count, pending-review
   count.
2. Inbox band. Hidden when `inbox/` is empty. Groups proposals by meeting, shows
   the quote under each, and offers accept, skip, accept all, skip all. Priority
   is editable before accepting.
3. Controls. Grouping toggle for horizon, person, project. Owner filter for mine,
   waiting on, all. Priority filter. Hide done.
4. Quick add. Text, project, owner, priority, due.
5. The grouped list.

Default grouping is horizon. A row shows a checkbox, a priority badge that cycles
P0 to P1 to P2 on click, the text, project and person chips, and the due date.

Person grouping keys on the person the loop is *with*, which is not the same as
`owner`. An item Filippo owes David has `owner: "me"` and
`source.person: "David"`, and it belongs under David, because the point of that
grouping is to open the page before a 1:1 and see everything live between the two
of them. So the key is `source.person`, falling back to `owner` when
`source.kind` is `manual` and no person was set, and to "No person" otherwise.

The owner filter reads `owner` directly. "Mine" is `owner == "me"`, "waiting on"
is everything else.

Group order under horizon grouping is fixed: overdue, today, this week, this
month, someday. Empty groups are hidden. Under person or project grouping, groups
sort by open count descending.

Styling follows the reference artifact's token approach. Colours are defined on
`:root`, redefined under both `@media (prefers-color-scheme: dark)` guarded by
`:root:not([data-theme="light"])` and `:root[data-theme="dark"]`. The page works
at phone width with a 16px gutter and no horizontal scroll.

## Error handling

- Losing the db connection sets a visible status line and stops accepting edits.
  The page does not silently drop writes.
- A write that fails restores the previous state and shows what went wrong.
  `quota_exceeded` gets its own message asking the user to clear done items.
- Opening the page outside Claude, where `claude.use("db")` returns nothing,
  shows a short explanation and hides the add form rather than rendering an
  empty list that looks like real data.
- The sweep updates `meta/sync` only after its inbox writes succeed. A crash
  mid-run re-reads the same meetings next time, and dedupe absorbs the repeat.

## Verification

No test framework exists in em-hub, so verification is manual and uses real data.

1. Publish the page and confirm it renders empty without errors.
2. Seed `items/` and `inbox/` from the September 2026 analyses under
   `people/david-manager/`, `people/vlad-engineer/`, `people/andrey-direct/` and
   `people/victor-jalencas/`.
3. In a browser: tick an item done, cycle a priority, accept an inbox item, skip
   another, switch all three groupings, apply each filter, add an item by hand.
   Reload and confirm every change survived.
4. Check phone width.
5. Check dark mode.
6. Run the sweep prompt once by hand against real Granola data and inspect what
   lands in `inbox/` before any routine is scheduled.

## Build order

1. Page and schema, published, empty.
2. Seed from existing analyses. This is the first real test of the schema.
3. `/todos` skill.
4. `/1on1-lifecycle` step 4.5.
5. Sweep prompt, run by hand.
6. Cloud routine, only after the assumption above is verified.

Steps 1 and 2 are worth having on their own. If the sweep turns out to need a
local job instead of a cloud routine, nothing earlier in the list is wasted.
